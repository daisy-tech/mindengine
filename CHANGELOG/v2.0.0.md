# MindEngine v2.0.0 — 完整重构首版

> 发布日期：2026-06-07
> 代号：**小白 / XiaoBai**
> 与 legacy MindMem v0.97 的关系：行为基准等价，工程实现完全重写。

## 概览

MindEngine v2.0.0 是 legacy **MindMem v0.97** 的全量重构（rebuild）首个 GA。
保留了"AI 记忆是一等公民"的产品形态，把工程代码从 ~10k 行压到 ~7k 行，
同时把 AI 伙伴正式更名为 **小白（XiaoBai）**，
并以 **Postgres + pgvector** 取代了 legacy 的 SQLite + Mem0/Qdrant 双栈。

## 里程碑亮点

| 里程碑 | 内容 |
| --- | --- |
| **M1** 脚手架 + 域模型 | 全部 `domain/`、Repository Protocol、Postgres + pgvector + Celery + Alembic |
| **M2** 核心聊天链路 | Memory Router 三层、PromptComposer、人格契约、SSE 流式 + 断连必落（D2） |
| **M3** 四层记忆 + 异步抽取 | profile / event / episodic / relationship 四层 Repo、Celery `memory.*` 任务 |
| **M4** 纠错管线 + 评测实验室 | LLM-driven 纠错管线、L0/L1 规则、归因、合成评测、`/api/eval/*` 端点 |
| **M5** 前端 + 上线对齐 | 全新 Vue3 + Element Plus 前端（5 视图）、SSE 心跳、品牌 = 小白 |

## Breaking changes（与 legacy MindMem 相比）

1. **AI 名称**：`MemoBot` → `小白 / XiaoBai`。
   - `BASE_PERSONA` 改写、抽取/纠错 prompt 自称改写。
   - 头像沿用同一张 PNG，仅文件名 `memobot-avatar.png` → `xiaobai-avatar.png`。
2. **存储后端**：`SQLite + Mem0(Qdrant)` → `Postgres + pgvector`。
   - episodic 向量直接落入 `episodic_memories.embedding vector(...)` 列，HNSW 索引。
   - 不再依赖 Mem0 / Qdrant，部署侧少一个外部服务。
3. **SSE 持久化（D2）**：客户端断连不再丢失 `prompt_meta`。
   只要 LLM 产出 ≥ 1 token 就会有一条带 `meta_json` 的 message 落库，
   评测可重放任意中断 turn。
4. **纠错链路（M4）**：`intent=correction` 与 memory extract 互斥
   （之前两者会 race，导致刚刚弃用的事实立刻被重新写回）。
5. **评测实验室（M4）**：合成评测 + 真实聊天评估都走 `chat_audit_v1` schema，
   落盘文件统一 `0o644` + 路径穿越校验。
6. **OpenAPI title**：`MemoBot API` → `MindEngine API`。
7. **前端**：legacy 前端代码已退役。MindEngine 提供全新 Vue3 + Vite + Pinia + Element Plus 前端，
   位于 `frontend/`，`docker compose up frontend` 一键启动。

## 数据迁移

> ⚠️ MindEngine v2.0.0 **不直接读取 legacy MindMem v0.97 的数据库**。

如果你需要从 legacy 升级，请按下列顺序操作（不在仓库里硬编码迁移脚本，
因为每个部署的 legacy 数据形状不同）：

1. 从 legacy 导出 `users / conversations / messages / episodic / events / profile / relationships`。
2. 用 `scripts/migrate_from_legacy.py`（待用户落地）按字段映射逐条 upsert 到 Postgres。
3. episodic 向量需要重新跑 `extract_episodic` 任务（embedding 模型已升级）。
4. 跑 `pytest -k smoke` + `docker compose exec backend python scripts/smoke_m4.py` 验证链路。

# v2.0.1 — 密码重置路径

> 发布日期：2026-06-13

针对 PoC 阶段「忘记密码只能进数据库改」的问题，补齐三条用户级路径。
PoC 暂未接入邮件服务，所以没有「邮件链接重置」流程；这条限制由登录页对话
框直接告知用户。

| 场景 | 入口 | 凭据 |
| --- | --- | --- |
| 已登录想换密码 | 侧边栏「修改密码」对话框 → `POST /auth/change-password` | 需提供 current_password |
| 忘记密码、有服务器权限 | `docker compose exec backend python scripts/reset_password.py --email <e> --password <p>` | shell 即凭据 |
| 忘记密码、纯客户端 | 登录页「忘记密码？」对话框，引导联系管理员 | — |

**变更明细**

- `backend/app/services/auth/service.py`：新增 `AuthService.change_password()` 与 `admin_reset_password()`，复用既有最小密码强度策略。
- `backend/app/api/auth.py`：新增 `POST /auth/change-password`（204 / 401 / 400）。
- `backend/scripts/reset_password.py`：交互式 / 命令行重置 CLI，支持 `--password` 或两次 `getpass`。
- `backend/Dockerfile`：runtime stage 新增 `COPY scripts /app/scripts`，避免下次重 build 丢脚本。
- `frontend/src/components/ChangePasswordDialog.vue`：自助修改密码弹窗。
- `frontend/src/views/LoginView.vue`：登录页加「忘记密码？」入口 + 重置说明对话框。
- `frontend/src/api/auth.ts`：增加 `changePassword()` API 客户端。
- 测试：`backend/tests/unit/services/test_auth.py` +6 项，`backend/tests/integration/test_auth_api.py` +4 项。`pytest` 共 392 passed。

**安全模型**

- `change-password`：要 JWT，且要正确的 current_password；防止只持有 token 的攻击者悄悄改密。
- `admin_reset_password`：仅 CLI 暴露，不挂在 HTTP 上；信任「能 `docker exec` 进容器」即认证。
- 两条路径都走 `_check_password_strength`（≥ 8 字符）和 Argon2id 哈希，与注册一致。

# v2.0.2 — 合成评测端点接通

> 发布日期：2026-06-14

补齐 lifespan 注入,把 `POST /api/eval/synthetic/{name}/start` 从「永远 503」状态修复成可用状态;并把 smoke / full 评测用例数据补齐。

**症状**

- 之前调用 `POST /api/eval/synthetic/smoke/start` 一直返回
  `503 — synthetic runner is not configured`,因为 `app.state.synthetic_runner`
  从来没在 `main.py::lifespan` 里被注入。
- `eval/cases/smoke_cases.json` 只有 8 条,意图覆盖不全;`full_cases.json` 缺失。

**变更明细**

- `backend/app/services/eval_synthetic/runner_chat.py`(新增):`ChatBackedSyntheticRunner` 实现 `SyntheticCaseRunner` 协议——把一个 `EvalCase` 串过 `MemoryRouter → PromptComposer → chat LLM`,不持久化、不分发后台任务。`case.history` 进 LLM messages,同时回写到 `outcome.activated_keywords` 让 `must_activate` 检查在合成路径下也有意义。
- `backend/app/services/eval_synthetic/__init__.py`:导出 `ChatBackedSyntheticRunner`。
- `backend/app/main.py::lifespan`:构造 `ChatBackedSyntheticRunner` 实例,挂到 `app.state.synthetic_runner`(进程内单例,无每请求状态)。
- `backend/eval/cases/smoke_cases.json`:从 8 条扩到 20 条,9 个意图 × 3 种人格全覆盖。
- `backend/eval/cases/full_cases.json`(新增):55 条用例,覆盖各意图边界、多轮纠正、虚构防护、记忆召回等场景。
- `backend/tests/unit/services/eval_synthetic/test_runner_chat.py`(新增):6 项单测覆盖 happy path / hard rule 命中 / history 透传到 LLM / 关键词回填 / LLM 异常容错 / personality 透传。
- `backend/selftest/run.py` Tier 2E:新增「runner 已注入」轻量检查——用非 eval_user_id 调 `start` 端点,期望 403(身份校验生效),而非 503(runner 缺失)。这条 sanity check 不耗费 LLM 调用,但能立即发现 lifespan 漏注入。
- `backend/selftest/refresh-and-run.sh`:把 `app/main.py`、`app/services/eval_synthetic/`、`eval/cases/` 一起 cp 进容器,避免 ECS 上忘同步。

**身份策略**

`/api/eval/synthetic/{name}/start` 改成软校验:`allow_destructive_dev=True` 时任何已登录用户都可以调,前端「开始评测」按钮直接可用。理由是 `ChatBackedSyntheticRunner` 是只读的 —— 不写库、不发 celery 任务、router cache 写在 `settings.eval_user_id` 名下而非 caller 名下,所以"谁来调"对真实数据零影响。生产模式(`allow_destructive_dev=False`)依然 pin 在 EVAL_USER_ID 上做防御性兜底。

`/api/eval/seed-persona` 仍然走严格的 `_ensure_eval_user` —— 它会真的 wipe 并重建 EVAL_USER_ID 的 4 层记忆,放开会出大事。

执行顺序也调整了:`start_synthetic` 第一行先做 runner-injection 检查再做身份校验,这样"lifespan 漏注入"能在任何 caller / 任何 case name 下首先暴露成 503,selftest 的轻量 sanity ping 才有意义。

**怎么验证**

```bash
# 容器侧 sanity:不再 503
./selftest/refresh-and-run.sh

# dev 模式(.env 里 ALLOW_DESTRUCTIVE_DEV=true):用任何账号登录,前端「开始评测」即可
# 生产模式:必须登录 EVAL_USER_ID
curl -X POST -H "Authorization: Bearer $EVAL_TOKEN" \
  http://localhost:8000/api/eval/synthetic/smoke/start
# → 200,返回 SyntheticReport(总数、通过率、混淆矩阵、逐 case 明细)
```

**已知限制 & 后续工作**

- 同步阻塞:当前 `start` 端点会在请求里跑完整批 case(20 条 ≈ 30~60 秒)。后续若上 full(55 条)需要改成「返回 run_id + 异步轮询 / WebSocket」。
- 合成路径不依赖真实 4 层记忆——`ctx = MemoryContext()` 是空的。如果要测「记忆真的从 4 层取出来」,先调 `POST /api/eval/seed-persona` 把 EVAL_USER_ID 的 4 层 seed 好,然后写期望命中 seeded 持久 fact 的用例。

**v2.0.2.3 — 记忆页 UI 修缮 + 关系抽取防编名字**

用户反馈三处:(1) 情景标签下两条记录都是空的;(2) 画像基础信息直接显示英文 schema 字段(`name: 小晶 · birth_year: 1983 · gender: null · location: 北京`),夹带 null;(3) 关系图谱里出现莫名其妙的英文名 "xiao"。

根因分别是:

- **情景空**:前端 `EpisodicMemory` interface 错误地声明了 `title` / `content`,但后端域模型字段叫 `text`。表格 `prop` 取的字段全部 undefined,所以渲染出空行。
- **画像英文**:`MemoryView::fmtKv` 是通用 key:value 拼接,没有字段中文映射,也不过滤 null。
- **关系姓名错乱**:`Relationship.name` 是 LLM 抽取阶段直接写入的,worker 落库不会修整。原 prompt 例子里写「妻子张三、儿子小宝」,模型容易把"称谓 + 名"作为单 token 整体输出,且当用户没说全名时模型会自由发挥(从拼音、用户名截字、甚至凭空编)。

**变更明细**

- `frontend/src/api/memory.ts::EpisodicMemory`:字段对齐后端,改为 `text: string`(并加上 `source` 等可选字段)。
- `frontend/src/views/MemoryView.vue`:
  - 画像 tab 重写:用 `dl + dt/dd` 中文标签布局,字段中文化(姓名/出生年/性别/所在地/职位/行业/级别/家庭构成/备注),`gender` 值 `male/female/other → 男/女/其它`,null/空数组/空字符串一律不渲染。`occupation/family_structure` 整段在没有任何有效字段时不显示。
  - 情景 tab:`prop="text"`,加 `source` 列(extract_episodic / user_corrections 等),长内容自动 ellipsis + tooltip。
  - 关系 tab:加 `via`(经由)和 `created_at`(录入时间)两列、`attributes` 列改为「key:value · key:value」紧凑格式,空 attributes 显示「—」。空状态增加排查提示文字。
- `frontend/src/views/SocialGraphView.vue`:节点圆圈内文字按字符宽度截断(中文 4 字 / 英文约 7 字),超出加省略号;完整 label 通过 SVG `<title>` 暴露给鼠标悬停。
- `frontend/src/styles.css`:新增 `.kv-list` 网格排版样式(100px 标签 + 1fr 值)。
- `backend/app/services/memory_extract/relationship_extractor.py`:重写 prompt 的 name 字段约束。明确禁止「凭语境编姓名 / 用户名取拼音 / 把"小"扩成 xiao」;用户没给名字时 name 必须直接写称谓("妻子"、"儿子")。已给的名字保留原文(中文/英文/拼音不做转写)。
- `backend/selftest/refresh-and-run.sh`:cp 列表加上 `app/services/memory_extract`(同时同步到 backend 和 celery 容器)—— 之前漏 cp 这层,改 prompt 不会进容器。

**3 ("xiao") 没法在没有原始数据的情况下下定论**

prompt 防护可以堵住「未来再发生」,但已经写进数据库的 `xiao` 这条数据需要你提供:

1. `GET /api/memory/relationships` 的完整返回(走「关系」表格 tab 看 `name / role / via / 附加属性 / 录入时间`,或浏览器 devtools 抓接口)

**Hotfix:NFS AppleDouble 元数据导致 `GET /api/eval/synthetic` 500**

`backend/eval/cases/` 目录在 NFS / macOS 共享上会被生成 `._smoke_cases.json` 这种 4KB AppleDouble 二进制元数据。`docker compose cp ./eval/cases backend:/app/eval/` 会把它一起带进容器,然后 `Path.glob("*.json")` 把它当成 JSON 文件喂给 `read_text(encoding="utf-8")` —— UnicodeDecodeError 不是 `CaseLoadError`,从 `list_synthetic` 漏出去变 500,前端「合成评测」标签页打不开。

修法:

- `case_loader.list_case_files`:跳过任何 `.` 开头的隐藏文件(AppleDouble、临时文件)。
- `case_loader.load_cases`:把 `UnicodeDecodeError` / `OSError` 都包成 `CaseLoadError`,让上层的「skip on CaseLoadError」语义真正生效。
- `selftest/refresh-and-run.sh`:cp 前 `find ./eval ./app ./selftest -name '._*' -delete`,cp 后再在容器里 `find /app -name '._*' -delete`(防止历史残留)。
- `tests/unit/services/eval_synthetic/test_case_loader.py`:新增 2 条 —— `test_list_case_files_skips_appledouble`、`test_load_cases_non_utf8_raises_caseloaderror`。

## v2.0.2.5 — Hotfix:首句填 title 不生效

部署 v2.0.2.4 后用户反馈「会话还是叫『新对话』」。后端日志显示
`set_title_if_empty` 一直返回 False。根因不在后端,在前端两处:

1. **`ChatView.newConv` / onMounted 显式传了 `'新对话'` 当 title** —— 调用
   `chat.newConversation('新对话')` 时,前端把这串字符直接当 user-provided
   title 走 `POST /api/conversations`。后端创建时 row.title 就是「新对话」,
   `set_title_if_empty` 看到 `if row.title:` 为 truthy 直接 no-op,首句永远
   不会覆盖。
2. **chat store 的 `send()` 只 reload 当前消息,不 reload 会话列表** —— 即使
   后端真的写了 title,store 里 `conversations[i].title` 还是发送前的旧快照,
   侧栏要刷新整页才看得见。

修法:

- `frontend/src/views/ChatView.vue`:`onMounted` 和 `newConv` 两处的
  `chat.newConversation('新对话')` 全部改为 `chat.newConversation()`。后端
  收到 `title=null` 时 `set_title_if_empty` 才会工作。
- 同文件的模板:侧栏 `c.title || c.id` → `c.title || '新对话'`(原 fallback 是
  会话 ID `c_abc...`,极丑);主标题区从 `chat.activeConversation?.title || '请选择会话'`
  拆成两路 —— 没选会话显示「请选择会话」,选了但 title 还空显示「新对话」。
- `frontend/src/stores/chat.ts::send`:在 `reloadCurrent()` 之后,如果当前
  conv 的 title 还是空,补一次 `listConversations()` 把后端写回的 title 同步
  到 store 里。**有意只在 title 为空时拉**,避免每发一条消息都重拉列表。

部署后侧栏第一句话发完应该立刻变成「今天天气很好啊」之类的真实首句。

> 经验:**前端的「占位文案」和后端的「null sentinel」要么完全分开、要么共用一个**。
> 把 UI 占位字符串「新对话」当成 API 入参传过去,看似能跑,实际把后端的 null
> 通道堵死了 —— 这次的踩坑就是这个模式。

  改 inactive。如果后续要把 banned-entities 也用到关系层,要补一条
  「banned_entities 命中 → 关系自动 deprecate」的 hook。

## v2.0.2.8 — 情景/事件记忆去重(消除"奶黄"× 18)

**用户问题**:截图里「用户家里养了一只叫奶黄的猫」出现 3 次、「宅家学习AI」
出现 2 次(其中一条只多个句号)、「最近心情烦躁」+「最近感到烦惱」也属
同一情绪却各算一条。情景共 18 条里至少 5 条重复,事件 7 条里 3 条重复。

**根因**:抽取链路是**无状态、纯追加**的:
- `EpisodicExtractor` 只在自己的单次输出里做 `cleaned.lower()` 字面去重
- `EventExtractor` 完全不做去重
- worker(`run_extract_episodic` / `run_extract_event`)拿到 candidates 后
  **从不查库**,直接 `repo.add` / `repo.insert`,所以每聊一句"奶黄"都
  会再生一条新记忆

LLM 看不见库里已有什么 → 只能靠 worker 端在写之前查库。这次补这环。

### 1. 情景层 — pgvector ANN 去重

- **`EpisodicRepo.find_similar(text, threshold=0.90)`** 新方法
  - 复用现有 HNSW 索引和 `cosine_distance` 操作符,一次 ANN 找最近邻
  - similarity = 1 − distance/2,同一标度跟 `search` 一致
  - 返回 `EpisodicHit | None`:命中阈值就给一条命中证据,否则 None
  - 写法故意不复用 `search()`:这里只要 nearest-1 + 阈值,分支更清晰
- **`run_extract_episodic` 接 dedup_threshold**(默认 0.90,可在 settings
  里调):
  - 同批字面去重(set of `lower().strip()`):防 LLM 单轮自我重复
  - 跨轮次语义去重(`find_similar` 命中):跳过,不写新行
  - ANN 调用包了 try/except,失败时退回旧行为(不去重)避免连锁失败
  - 返回值多一条 `skipped_duplicate`(配合 banned 计数,链路清晰可观测)
- **新增 settings**:`episodic_dedup_threshold = 0.90`
  - 0.90 是中文 embedding 实测的合理起点 —— 同义改写能命中,但语序
    翻转的真新事实("用户养了奶黄" vs "奶黄陪用户")不会误杀
  - 阈值留一个钩子方便回归后期调

### 2. 事件层 — 标题归一 + 时间窗口

事件没有 embedding 字段(`events_table` 没有 vector 列,加列要做迁移
而且工程量大),所以走字符串归一:

- **`EventRepo.find_similar_recent(type_, title, within_days=30)`** 新方法
  - 拉最近 30 天内同 type 的 active 事件(默认上限 50 条)
  - 用 `_normalize_title` 剥首尾标点(中英文)+ lower:`"宅家学习AI."`
    `"宅家学习AI。"` `"宅家学习AI"` 全部归到同一 key
  - 字符串相等 → 命中
  - 子串包含(短的是长的子串,且 ≥ 4 字符)→ 命中:覆盖
    "宅家学习AI" vs "宅家学习AI 顺便陪猫"
- **`run_extract_event` 接 dedup_window_days**(默认 30):
  - 同批 (type, normalized_title) 去重(set):防单轮重复
  - 跨轮次 `find_similar_recent` 命中:跳过
  - 同样有 try/except 兜底
  - 返回值多一条 `skipped_duplicate`
- **新增 settings**:`event_dedup_window_days = 30`

**已知短板**:同义改写("心情烦躁" vs "感到烦躁")字符串去重抓不到。
这是 events 没 embedding 的固有限制,第二道防线靠 prompt(见下)。
真正长期解法是给 events 表加 embedding 列,迁移留 v2.0.3+。

### 3. 抽取器 prompt 微调 — 提醒不要复述

光靠 worker 兜底不够,LLM 自己就该少抽点重复。

- `episodic_extractor.py`:
  - 加一段「**不要复述上下文里"早就讲过"的旧事实**」
  - 给具体例子:history 已说"奶黄是用户的猫",新一轮"奶黄粘人"
    只抽"奶黄粘着用户",不再重抽"用户养了奶黄"

  - 同样加「**不要复述 history 里已经讲过的事件**」
  - 顺便加一条:title **不要带尾标点**("宅家学习AI" 不是
    "宅家学习AI。")—— 这是上面看到的 7 条事件里 2 条重复的真实

### 7. 历史去重 CLI(`scripts/dedup_memories.py`)

新代码只阻止**未来**的重复;**已经堆在库里的 18 条情景 / 7 条事件**
仍需一次性清理。新增独立 CLI:

```bash
# 默认全用户、--dry-run 预览 / 不写库
docker compose exec backend python -m scripts.dedup_memories --dry-run

# 真正写入(soft delete + memory_deprecations 审计行)
docker compose exec backend python -m scripts.dedup_memories

# 单用户 + 自定义阈值
docker compose exec backend python -m scripts.dedup_memories \
    --user-id 06b91a7f-... --episodic-threshold 0.93
```

参数:

- `--user-id`(默认所有 active 用户)
- `--episodic-threshold` 默认 **0.95**(故意比 worker 在线 0.90 严,
  CLI 一次性扫,宁可漏掉也别误删真新事实)
- `--event-window-days` 默认 **365**(历史扫描,不是 30 天的运行时窗口)
- `--no-episodic` / `--no-event` 任选其一关掉对应层
- `--dry-run` 只统计/打印,不动数据库

输出:

- stderr 给每个用户**人类可读**摘要(每层 scanned/kept/deprecated +
  前 10 条 dup→keep 配对)
- stdout 给完整 JSON 报告(含 totals 聚合,可重定向供 grafana 之类摄入)

**审计**:每次 deprecate 都同时:

1. `episodic_memories.status` / `events.status` 翻成 `'deprecated'`
2. 在 `memory_deprecations` 写一行 `action='deprecate'` +
   `reason='dedup_cli: similar to <keep_id> (sim=0.96 ≥ 0.95)'`(情景)
   或 `reason='dedup_cli: exact match with <keep_id> ...'`(事件)

`memory_deprecations` 表是 doc 06 §5 / 08 §2.4 已建好的 audit log,
本次复用,不新增表。这意味着误删可以从这张表里查回(人工 restore 把
status 改回 active 即可)。

**幂等**:扫描时已经过滤 `status='active'`,且加入 `deprecated_ids`
in-memory 集合,同一行不会被两次记账;在干净 DB 上重跑 0 改动。
